# End-to-end ownership: decision record

The testing strategy gives the Cypress journey one job: walk one customer or business-user journey per critical flow through the browser. It must not cover permutations, business rules, visual details, data consistency across systems, or any assertion on an API response. Back Office CRUD qualifies only as the one journey that proves a browser-only flow. Everything past that journey belongs to the facade test.

This file holds the decision for every `backoffice` and `api` spec on `master`, measured on 2026-09-29 at `bb737df2`. It also covers the 17 back-office specs arriving from the Robot UI migration, and flags the obvious cases in `yves`, `mp` and `smoke`.

## How a spec is classified

Every spec file gets exactly one class. The class says what happens to the file:

| Class           | The file                          | Its claims                                                                                                                     |
| --------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **KEEP**        | stays, trimmed to the one journey | anything past the journey moves, is dropped, or is a permutation, as listed per row                                            |
| **PERMUTATION** | goes                              | another kept spec already walks this journey. Anything the variant proves that changes an outcome moves to a cheaper test type |
| **MOVE**        | goes                              | admin CRUD, business rules and validation go to a cheaper test type. Visual checks are dropped, because no test type owns them |
| **API**         | goes                              | the API contract test, or the API golden path when the claim is deployment wiring                                              |

A back-office feature keeps one journey when at least one of these holds:

- it is on the order-to-cash or catalog-to-storefront path
- it has behaviour only a browser can exercise: drag and drop, JavaScript-built forms and selection tables, redirects across applications, session and cookie handling

Plain-form CRUD on peripheral configuration, such as measurement units, tax rates, file directories or search preferences, keeps no journey. The strategy's gap table covers this case: a browser-only flow that no journey walks carries the controller and form-binding gap knowingly.

Target test types use the strategy's names. Module paths are relative to `spryker/suite` `src/`. Facade tests live in `<Module>/tests/SprykerTest/Zed/<Module>/Business`. Self-Service Portal tests live in `SprykerFeature/SelfServicePortal/tests/SprykerFeatureTest/Zed/SelfServicePortal`.

"Exists" means an equivalent test was found and read. "Partial" names what is missing. "None" means nothing asserts the claim below Cypress. Effort for missing targets: **S** is under an hour on existing helpers, **M** is about half a day for a new tester, helper or fixture.

## Runtime and budget

Measured from the `cypress-timings-*` artifacts of two `master` runs of `SN-COMPATIBILITY-CI` in `spryker/suite` ([36578501276](https://github.com/spryker/suite/actions/runs/36578501276), [36573762743](https://github.com/spryker/suite/actions/runs/36573762743)). Every spec runs with `repositoryId=suite`.

| Lane part                                                               | Measured                                  |
| ----------------------------------------------------------------------- | ----------------------------------------- |
| Five sharded jobs, recorded spec time (112 specs)                       | 76.3 and 73.7 min, summed over the shards |
| of which `backoffice` (43 specs; the 6 SSP ones run in the `ssp` shard) | 25.5 and 24.9 min                         |
| of which `yves` (48) / `mp` (17) / `api` (4)                            | 32.1 / 18.7 / 0.0 min                     |
| `Run Tests` step per sharded job                                        | 17 to 23 min                              |
| `ssp` shard `Run Tests`                                                 | 11 min                                    |
| `Install Project` per job                                               | 11 to 13 min, fixed cost                  |
| Lane wall clock                                                         | about 42 min                              |

The `api` specs record 0 s in the suite lane because they run only for `b2b-mp`. `smoke` is not part of this lane: `cy:ci` excludes it, and it runs in the post-deploy workflow.

**Effect of this record.** Back-office live `it()` cases drop from 147 to 27, one per kept spec. The sharded back-office spec time drops from about 25 min to about 9 min. That estimate counts removed files at zero, and counts each kept spec at its first case plus 30 % of the rest for setup. The sharded lane goes from about 75 min to about 59 min of spec time, which is 3 to 4 min off every shard's wall clock.

**Budget decision.** The strategy commits to a budget, expressed as runtime and not as a count:

- The number is the summed recorded spec time of the sharded Cypress lane, read from the `cypress-timings-master` cache that `_cypress.yml` already aggregates. The `ssp` shard counts in the sum.
- The budget is **60 min**, the size of the lane once this record is applied. With five shards that is about 12 min of tests per shard, and a lane wall clock of about 30 min including the fixed install.
- A change that pushes the sum over the budget pushes something down or removes something first. The reviewer rule of step 5 on the strategy page stays as it is: a new journey needs a second reviewer who agrees that no cheaper test type can see the defect.
- The public page states that the budget exists and that CI enforces it, but not the number. The page is published on docs.spryker.com and carries no tier timing numbers by design. The number lives next to the lane that enforces it.

A count would go stale the same way the rejected journey list would. Runtime is what every added journey actually costs on every run, and the timings cache already measures it.

Two product findings came out of this work. They are reported, not fixed:

- The Self-Service Portal file upload advertises at most four files, but only as an HTML `max` attribute, which browsers ignore on file inputs. No server-side constraint limits the number of files.
- The attach-by-CSV fixtures the deleted specs uploaded had one column and a "to be detached" label in a data row. `RelationCsvReader` reads the first column as identifiers to attach and the second as identifiers to detach, so those uploads attached the label and detached nothing. The specs asserted only the success message.

## Findings raised while classifying

- **Coverage gaps that only Cypress hides today:**
  - Self-Service Portal inquiry approve, reject and cancel have no real state-transition test at any cheaper test type.
  - Category flag updates, tax-rate and discount form validation, and the `FileManagerGui` form have no test below Cypress.
  - The file upload `max=4` is only an HTML attribute. The server enforces no count constraint.
- **Fragile or wrong specs:**
  - The asset spec registers `cy.intercept` after the request it waits for has already fired.
  - `budget.cy.ts` "should see budget in the budget list after creation" asserts a pre-existing fixture budget, not the one it created.
  - `request-management.cy.ts` cases share mutable fixture state and depend on run order.
  - The skip label of `product-merchant-relation-management.cy.ts` says b2b, but b2b never runs it.
- **Specs that assert nothing about their variant:** `order-gift-card.cy.ts` never checks that a gift card code was created. `order-creation-dms.cy.ts` checks only OMS transitions.
- **Controller-only logic** (`AddAssetController::createSspModelForAsset`) can only be tested through the browser until it moves behind the facade.
